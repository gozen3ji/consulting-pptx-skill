# スライド作成ルール正典（HTML / PPTX 共通）

**これが唯一の正本。** スライドを作るすべてのスキル・ビルダーはここを参照する。
他のドキュメントと食い違う場合はこのファイルが勝つ。

> 背景: 同じ指摘（サブタイトル・角丸・ヘッダー細字・スライドサイズ）を何度も受けたことから生まれたルール集。原因は「ルールが複数のファイルに分散し矛盾している」「セッションごとに自作ビルダーを書き、前回のヘルパーの癖を引き継ぐ」こと。**新しいビルダーを書くのではなく、このルールに沿った既存ビルダーを流用し、出力前に機械チェック（後述）を必ず通す。**

---

## 0. 着手前（Define-before-Produce）

**標準フロー（4段。①→②の順を飛ばして型から入らない）**
1. **ストーリー設計** — イシューを問いの木（issue tree）に分解し、各問いへの答えを1行の主張として並べたストーリーライン（＝将来のタイトル列）を先に作って合意する。スライド枚数・型はこの後で決める
2. **型の適応** — 各主張に合う見せ方を38型カタログ（発想帳）から選ぶ。合わなければ自由記述で組む
3. **ファクト＆フォーマットチェック** — 数値・日付・固有名詞を一次ソースと照合（「見つからない」と「存在しない」を区別。実測値には測定条件）。フォーマットは check_deck FAIL 0 ＋ PDF全ページ目視
4. **AI癖の補正** — `references/ai-smell-lexicon.md`（AI slop語彙・構文・トーン）でセルフチェックし、check_deck の AI臭 WARN をつぶす


- 案件・テーマの知識ファイルを先に読む。憶測で作らない。
- 目的・成果物定義・スコープIN/OUT を3〜5行で提示してから作る（自明な依頼は除く）。
- 実体 > 体裁。薄いなら「薄い」と言う。
- **依頼の背景・期待値を先に確認する。** 誰からのどういうリクエストか・下書きレベルか提出版かを明示してから共有する。独立に作り始めると手戻りになる。
- **クライアント提出のスライドはレビューを通す。** 提出前に経験者とのレビューMTGを挟む。レビュー体制が組めない・負荷が重いときは、スライドでなく文書（Docs）形式で作って出す。

## 1. キャンバス

| 項目 | 値 |
|---|---|
| 比率 | **常に 16:9**。A4横（297×210）は使わない |
| PPTX | 13.333 × 7.5 in（12192000 × 6858000 EMU） |
| HTML | `.slide{width:338.67mm;height:190.5mm}` ＋ `@page{size:338.67mm 190.5mm;margin:0}` |
| PDF化 | `@page` を上記に合わせる。PDFページ数 = スライド数 |
| フォント | PPTX: 見出し明朝系／本文ゴシック系（例: Yu Mincho / Yu Gothic）。HTML: Noto Sans JP 系 |
| 色 | 自社ブランドパレットに統一。系統外の色を混ぜない。第三者・中立系列のみグレー系を許容 |

## 2. タイトル（メッセージライン）

1. **結論はタイトルに書く。タイトルは原則1行に収める。** PPTX（18.5pt）は1行・全角約40字以内。HTMLも1行に収まる長さまで詰める — `text-wrap:balance` は1行で足りる見出しを均等2行に割ってしまうので h1 には使わない。どうしても2行必要なときだけ、意味の切れ目で明示改行し、数文字だけの孤立折返しは禁止。
   - **nowrap は overflow:hidden と併用すると黙って切れる。** 納品前に各ページのタイトル右端が版面内に収まっているか確認する。
2. **体言止め。「〜です」「〜ます」で終えない。**
3. **主語と述語がわかる普通の文として読めること。**「〜は、…する」形。長い連体修飾で名詞に畳み込まない（例:「AとBを7層に整理した、賢さを作る知識層」✗ →「知識層は、AとBを7層に整理して賢さを作る」○）。「は」「を」を省かない。スローガン調に圧縮しない。「この」「その」「ここまで」で他スライドを参照しない（1枚で自立）。
4. **数だけを軸にしない。**「5種類のエージェント」ではなく実名を書く。
5. **タイトルを色分けしない。**
6. **タイトルだけを上から順に読んで1本のストーリーになること。** 出力前にタイトル一覧を抽出して通し読みする（機械チェックが一覧を出す）。
7. 「Step1 」等をタイトルに文字連結してタグ代わりにしない（右上タグチップで表す）。

## 3. サブタイトル・ラベル行（全面禁止）

- **タイトル直下の説明行・導入文を置かない。**
- **図・表の直上のタイトルラベル行を置かない。** 画像下キャプションも置かない。「何の表か」はスライドタイトル、またはカード/カラムの見出し帯で示す。
- ビルダーの `subtitle()` / `figttl()` は **no-op** にする。流用元に呼び出しが残っていないか機械チェック。

## 4. レイアウト構造

1. **1スライド=1メッセージ=1テーマ。** 2テーマあれば2枚に分割。
2. **上下に読ませない。** 関連しない内容の縦積み禁止。セクションは**左右に分ける**（各セクションに見出し）。
3. **1スライドに表は1つ。カード群の下に表を積まない。** 主役の表/図を左、補足コメントを右カラム（見出し付き）。
4. **図があるスライドは「左に図・右にコメント」の2カラム。** 図の下にコメントを敷かない。
5. **左右カラムの下端を揃える**（片側だけ短く右下が空く形は不可。stretch／`flex:1`）。
6. **左右カラムには関係が分かる見出し**（例: 左「システム全体構成」／右「この構成にした理由」）。
7. **左右に強い因果（前提→帰結）があるときだけ**横向き二等辺三角形を挟む。単なる表＋解説には入れない。
8. **スライド下部にメッセージボックス（GOAL/KEY/POINT の結論帯)を作らない。** 下部帯が許されるのは成果物チップ・実績ロゴ等の**内容物の列挙**のみ。結論はタイトルへ。
9. **囲みボックスを乱用しない。** 本文は地のテキスト、囲みは本当に立てたい1〜2要素だけ。
10. **ボックス羅列（カード3枚グリッド）ではなく軸のある表**（行=項目軸、列=観点軸）。左端の軸は意味のある粒度で大カテゴリに束ねる（rowspan）。
11. **左右2つのボックスを見比べさせない。** A社箱／B社箱 → 行=観点・列=比較対象の表に。
12. **内容が少なく下部に不自然な余白が出るスライドは垂直中央揃え。** 図が大きいページは上詰め。
13. **「まとめ」と「ディープダイブ」を分ける。** 冒頭に全体マップ（各行に「→ P.n」参照）を置き、後続の全スライドに右上タグチップで章対応を付ける。タイトルは接続語で前のスライドを受け、**通し読みでスピーチ原稿として成立させる**。
14. **目次は1列**。
15. **並列カード・ボックスは縦幅とスペースを完全に揃える**（`grid-auto-rows:1fr` 等で機械的に）。
16. **並列要素は内容の粒度・主語も揃える。** 主体・抽象度が食い違う並列は不可。全カードを同じ観点文型で書く。
17. **ステップ×実現手段は上下の箱で見せずテーブルに。** 左列=段階、右列=それを実現する手段。
18. **プロセス・段階は矢羽（シェブロン）チャートを第一候補にする。**
19. **1デッキ内でスライドテンプレートを統一。** 複数ソースから合体させたら必ず全ページを同一テンプレートに寄せる。
20. **「意味合い（So what）」は最下部の帯でなく右側セクションに置く。** 左=事実・チャート、右=意味合い・示唆の2カラム。
21. **左右カラムの見出しは上端を揃える。** 左がテーブルなら右カラムの見出しは th と同じ上パディング・同じフォントサイズ・同じ太さの下罫線にし、ベースラインと罫線の高さを一致させる。テーブルを `flex:1` で伸ばすときは `tr:first-child{height:1px}` でヘッダー行を最小固定に。
22. **価格・費用感の stat ボックスは右カラムの最下部に置く。**
23. **1カラム＝1見出し。** 見出し帯を2段重ねない。内側の構造はブレットのインデントで表す。
24. **最後のスライドにメッセージを載せない。** 締めは裏表紙（ロゴ＋連絡先のみ）。CTA・結論はその手前の通常スライドへ。
25. **rows・表のセルに2文以上の長文を流し込まない。** 2文以上になるなら「•」のブレットに分解する。
26. **矢羽の下に別内容の2カラムを積まない。** プロセス＋コメントは「左=縦のステップフロー・右=コメント」の2カラムに。軸タイトルは左右をまたぐ1本の太下罫付きで両カラムの上に。右カラムが短いときはブレットのみ縦中央寄せ（見出しの高さは左と揃えたまま）。
27. **前提→帰結の2カラムは横三角矢印で因果を明示する。** 右カラムの見出しは「だから、◯◯」の帰結形に。
28. **宙ぶらりんのフローティングオブジェクトを置かない。** ラベル・チップ・小要素を版面に浮かせて置かず、必ず表・カラム・チャートの構造の中に組み込む（例: 分類ラベルは表の行・列見出しに入れる）。
29. **懸念点・リスクを出すスライドには回避策・対応をセットで付ける。** 懸念の列挙だけで終えない。「リスクが低い理由」と「リスクへの対応」のように性質の違う内容は混ぜず、スライドを分ける。
30. **レビューコメント・宿題事項は本編スライドに残さない。** 末尾の「レビュー論点一覧」スライドに集約して宿題回答の目次として使う。先方レビューのまとめだけのページは本編でなく Appendix へ。

## 5. ボックス・色・凡例・枠線

1. **角丸禁止。** カード/ボックス/チップは直角 rect（PPTX `MSO_SHAPE.RECTANGLE`、`prst="roundRect"` を生成しない）。HTML `border-radius:0`。例外は高さ 0.4in 未満の小さなステータスピルのみ。
2. **ボックスの色を変えるなら同一スライドに凡例**（色チップ＋意味）。意味のない「見た目の強調」ダークカード禁止。
3. **塗り（背景色）のあるボックスに枠線を付けない。** 塗り自体が領域を示すので枠線は冗長。枠線は塗りなし（白背景）の要素だけ。
4. **罫線は「その先に区切る対象がある場所」にだけ引く。** 最終行の下、スライド最下部には引かない。「枠線＋塗り」「行き先のない罫線」は無思考な装飾に見える。
5. **比較表のハイライトは勝っている側**に付ける。自社列だけ常に色付きは不可。
6. **競合比較には相手が勝つ軸を必ず入れる。**
7. **自社実測値には測定条件の注釈**（対象・件数・検証主体）。
8. 意味を持つ色（✕赤・追加緑）はリカラー時も保持。製品UIスクショは無加工。
9. **色分けのカラーパレットにはモノトーン（グレー系）を含める。** 全カテゴリを有彩色で塗り分けない。基準・中立・非強調の系列はグレーで受け、有彩色は立てたい系列だけに使う。

## 6. 表

| 項目 | ルール |
|---|---|
| ヘッダー | **本文より2pt大きく・太字・濃色**。背景塗りつぶしなし。**軸は塗りでなく罫線で表現**: 見出し行の下に太い濃色罫（1.8px） |
| 行 | ゼブラ・強調行の薄背景なし。行間は細い薄色罫線1本 |
| 罫線 | ヘッダー下＝太い濃色、行間＝1px薄。**最終行の下は罫線なし**（`tr:last-child td{border-bottom:0}`） |
| 列名 | 省略語・造語禁止。各セルが何を指すか単独で分かる自然語。泣き別れしない |
| 本文サイズ | **表の本文は 11.5pt 以上、th は 13pt、行見出しは 12.5pt**。**図解・ダイアグラム内の本文も 9pt 以上**。10pt 台前半は投影・PDF で小さすぎる。小さくてよいのは脚注と図中ノードラベルのみ |
| 行の縦伸び | 行数の少ない表を `flex:1` で伸ばすときは `td{vertical-align:middle}` |
| 出典 | タイトルや表名に書かない。スライド下部の `出典：…` 行へ |
| 軸の見せ方 | 行見出し軸（左端列）は太罫線＋本文よりひと回り大きいフォントで「ここが軸」と分かるように |

## 7. 文章・ラベル

1. **丸括弧（）を多用しない。** 補足は「—」「・」「／」や文で。
2. **勝手な短縮・造語禁止。** 一読で伝わる完全な自然語。
3. **ブレット**: 文章化した段落は分解。行末数文字の泣き別れは圧縮。マーカーは第1階層「•」＋ぶら下げ、第2階層「–」＋ぶら下げ。「・」はマーカーに使わない。補足・理由・但し書きは並列に並べず、親ブレット配下のネストで表現。
4. **ブレットの語尾は同じ階層内で必ず揃える。ですます調は使わない。** 体言止めなら全部体言止め。階層ごとに型を決めるのは可（第1階層＝動詞止め・第2階層＝体言止め等）。
5. 脚注的な小さな注記も極力本文へ統合。
6. **用語統一（表記ゆれ禁止）**:
   - **1資料1用語。** 同じ概念に複数の表記を使わない（例: メモリ/メモリー、紐づけ/紐付け、ユーザー/利用者、フォルダ/フォルダー）。作成後に全文の表記ゆれスキャンをかける（check_deck が代表ペアを検出）。
   - **略語は初出でフル表記に併記してから使う**（例:「ワークスペース（WS）」と定義し、以降は WS 可）。定義なしの略語・内輪でしか通じない造語を使わない。
   - **AI生成資料はそのまま出さない。** 納品前に人間が読み手の視点で再鑑する（読み手は誰か・何を理解/判断してほしいか）。提出物では必須。
7. **比喩的・造語的な用語には「」を付ける。** 「劣化」「汚染」のような転用語は鉤括弧で括り、資料内のどこかで意味を定義する（略語定義と同じ扱い）。
8. **最終聴衆に「どこをチェックしてほしいか」を明示する。** レビュー用資料は機能の網羅列挙でなく、読み手にチェック・判断してほしい論点を明示したストーリー構成で作る。網羅的に作ると工数が膨れる — 会議体での説明＋質疑ベースでよい場面を見極める。
9. **AI臭ワード・言い回しを除去する。** 空虚な強調（まさに/非常に/極めて）・カタカナ盛り（ソリューション/シナジー/シームレス）・定型締め・三点セット構文・絵文字/信号機色の装飾は「AIが書いた感」の典型。語彙・構文・トーンの全リストと30秒セルフチェックは `references/ai-smell-lexicon.md`。check_deck が高確度語を WARN 検出する。

## 8. 出力前の機械チェック（必須）

```bash
python3 scripts/check_deck.py out.pptx   # または deck.html
```

チェック項目（FAIL が1つでもあれば直してから納品）:
- [ ] 16:9 サイズ（PPTX 12192000×6858000 / HTML 338.67mm×190.5mm）
- [ ] タイトル末尾が です/ます でない・40字以内・空でない
- [ ] roundRect が存在しない（小ピル除く）／HTML に `border-radius` ≥ 4px のボックスがない
- [ ] `subtitle(` / `figttl` / `.sub` 系クラスが残っていない
- [ ] 表ヘッダーが本文より大きく太字
- [ ] 最終行の下に罫線がない／塗りありボックスに枠線がない
- [ ] タイトル一覧を出力 → **人手で通し読みしてストーリーが繋がるか確認**
- [ ] ページ番号連番。「→ P.n」参照がある場合は挿入後に振り直し済み

**HTMLレイアウト検査**: `node scripts/check_layout.mjs deck.html` — フッターと本文の重なり・右端/下端のはみ出しを実レンダリングで検出。

その後の目視QA（PDF化→画像化して全ページ確認）で、孤立折返し・はみ出し・重なり・左右下端の不揃い・凡例の有無・余白バランスを確認する。
